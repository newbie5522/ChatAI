# Codex × WorkBuddy 协作协议

## 唯一事实源

GitHub 是唯一实时事实源。聊天内容、个人笔记和未推送代码不代表项目状态。

每次开工必须：
1. 阅读 MASTER_PLAN、STATUS、相关 ADR 和 Issue。
2. 同步 main，确认目标文件没有其他进行中 PR。
3. 在 Issue 留言：执行端、所用模型、分支、计划、预计影响文件。
4. 将 Issue 状态理解为 Open；只有合并并验收后才可关闭。

每次交付必须：
1. 一个 Issue 一个分支，分支名建议 `v2/<issue>-<slug>`。
2. PR 标题包含 Issue 编号，正文使用 `Closes #N` 或 `Refs #N`。
3. 附测试命令、结果、截图/日志、数据库迁移与回滚说明。
4. 更新 STATUS；若改变架构，先增加 ADR。
5. 禁止执行端自行合并自己的高风险 PR。

## 模型与额度分配

| 工作类型 | 首选 | 原因 |
|---|---|---|
| 跨模块核心实现、网关、状态机、迁移集成 | Codex | 需要直接操作仓库、持续验证和端到端收口 |
| 架构、schema、并发、失败路径、安全评审 | WorkBuddy + Claude | 适合长上下文审查与反例推演 |
| 独立 UI、测试补齐、解析 Worker、机械迁移 | WorkBuddy + GPT | 边界清晰，适合并行实现 |
| 小型格式化、文档、测试数据 | WorkBuddy 中成本最低的 GPT | 避免消耗高阶模型额度 |
| PR 最终门禁 | 非作者端复核 | 交叉监督，避免自证正确 |

不要让两个执行端同时实现同一任务。Claude主要做设计与审查，GPT主要做边界明确的实现；复杂集成留给Codex。


## 冲突与偏离

- 同文件冲突：后开始的一方暂停，在 Issue 协调。
- 接口冲突：以已批准 ADR 为准。
- 发现方向不合理：不得边写边改方向，先提交 ADR 草案。
- 测试失败：不得标记完成。
- 只有口头说明、没有提交/PR/日志：视为未完成。
